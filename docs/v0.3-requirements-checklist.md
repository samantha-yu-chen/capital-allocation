# V0.3 Requirements Checklist — §88 MUST Items + Eight UI Tabs

Status: draft for review. This is a planning/audit artifact, not an implementation.

## Purpose and scope

This checklist supports the acceptance audit called for by `implementation-work-packages.md`
package 10 ("Audit every section 88 MUST against implementation and tests"), and gives every
package a shared definition of done while work is in progress.

**This document does not:**

- implement any engine (tax, ledger, Monte Carlo, property, solver, allocation, scenario, or
  attribution logic);
- define or amend the shared input/result schemas, ledger interfaces, or market-path interfaces —
  those are package 1's authority (`lifetime-capital-allocation-fire-optimisation-spec-v0.3.md`
  §83, owned by the scaffold/contracts package);
- treat the prototype (`design/Web page UI specification/engine.js`, `support.js`) as a source of
  production modelling assumptions. Its pooled accessible assets, simplified single-band Scottish
  tax, fixed ~6%/yr GIA drag, small simulation counts (300–700 paths), and year-1-only rent/buy
  snapshot are illustrative only and are called out below wherever they must not be copied forward.

Sources: `docs/lifetime-capital-allocation-fire-optimisation-spec-v0.3.md` ("spec", section
numbers below refer to it) and `design/Web page UI specification/Lifetime Capital Allocation &
FIRE Model.dc.html` ("reference design").

Each item below carries: the spec sections that define its acceptance detail, the
work-package owner suggested in `implementation-work-packages.md` (for traceability only — not
authoritative on its own), checkable acceptance criteria, and any ambiguity worth resolving before
or during implementation.

## Part A — The 29 §88 MUST requirements

### 1. UK tax model
Spec: §35, §78, §86 · Package 1

- [ ] Income tax, NI, personal-allowance taper, dividend tax, CGT, and pension relief are each
      implemented as isolated, independently testable functions (§35's suggested function list),
      not inlined into simulation logic.
- [ ] Tax rules are versioned by jurisdiction and tax year, with sources/effective dates recorded
      (work-packages §1).
- [ ] Known-example deterministic tax tests pass (§86 "Deterministic Tests").

**Ambiguity:** §35 lists calculation primitives but not a definition of "support boundaries for
tax cases" beyond "must be defined explicitly" (work-packages §1). What income/gain ranges,
allowances-tapering edge cases, and negative/zero-income inputs are in vs. out of scope needs an
explicit, written boundary before tax tests can be considered complete.

### 2. Scotland support
Spec: header (p.1: "Scotland + Rest of UK"), §35 · Package 1

- [ ] Scottish income-tax bands are modelled as a distinct, versioned configuration from
      rest-of-UK bands.
- [ ] Jurisdiction is a per-profile input (§78 `tax_region`) that changes which band table is used.

**Ambiguity:** §88 item 2 names only "Scotland support," but the document header and
work-packages §1 ("Create versioned Scotland/rest-of-UK tax configuration") both require
rest-of-UK too. Confirm rest-of-UK is in the v0.3 MUST scope, not an optional extra — the
reference design's footer note only mentions "Scottish income tax bands," which reads as
Scotland-only and should not be taken as the production scope.

### 3. Salary and spending
Spec: §20–21, §78 · Packages 1–2

- [ ] Gross salary, salary growth, and monthly living-cost inputs exist and flow into the annual
      investable-surplus calculation (§20, §31).
- [ ] Baseline per-person monthly expense range (£1,300 / £1,650 / £2,000) is configurable, not
      hard-coded (§21 explicit instruction).

### 4. Essential vs discretionary expenses
Spec: §24, §78 · Package 2

- [ ] Spending is split into essential and discretionary components as separate inputs.
- [ ] Monte Carlo/solver logic can flex discretionary spending independently of essential spending
      (§24: "Monte Carlo FIRE should support spending flexibility").

**Ambiguity:** the spec doesn't state what "supporting flexibility" means operationally — e.g.
can discretionary spending be cut dynamically mid-simulation in bad years, or is the flexibility
only expressed through the floor/target/comfort levels (§25) evaluated as separate static runs?
V0.3's permitted simplification list (work-packages, "Explicit scope boundaries") excludes
"dynamic withdrawal strategies," which suggests the latter (static levels only) — worth confirming
explicitly since it bounds what item 4 + item 25's spending levels must deliver together.

### 5. £1,300 / £1,650 / £2,000 monthly expense scenarios
Spec: §21, §61, §63 · Packages 2, 6, 8

- [ ] The three monthly figures are runnable as distinct spending scenarios, each producing its
      own FIRE age @ target success and required salary (§61 table).
- [ ] The same three levels appear as one axis of the required scenario matrix (§63).

**Ambiguity:** §21 labels the figures `monthly_per_person`, but the example profile (§79) and
reference design apply a single such figure directly as household `spendingCurrentMonthly` for
a one-adult household — i.e., no per-person multiplication is demonstrated anywhere in spec or
design. §22 explicitly warns against `2 people = exactly 2 × individual cost` and requires shared
vs. per-person cost splitting. Confirm whether the three baseline figures are (a) a per-person
input multiplied through the §22 household model, or (b) a household-level shortcut used only
when household size = 1. This affects every downstream MUST item that consumes spending.

### 6. Pension
Spec: §37–38, §78 · Package 1 (tax relief) / Package 2 (ledger)

- [ ] Employee/employer contribution, employer match, salary-sacrifice, annual allowance, access
      age, and estimated withdrawal tax are all modelled inputs (§37).
- [ ] The model detects marginal tax-rate bands and identifies high-value contribution zones from
      tax configuration rather than a hard-coded £55k-specific rule (§38, explicit instruction).
- [ ] Pension value calculation reflects tax saved, NI saved, employer contributions, tax-free
      compounding, and future withdrawal tax as distinguishable components (§37).

### 7. ISA
Spec: §39, §78 · Package 2

- [ ] Annual allowance and allowance-used tracking exist per year.
- [ ] No UK CGT, dividend tax, or withdrawal tax is applied to ISA holdings; ISA is treated as
      accessible capital (§39, §41).

### 8. GIA
Spec: §40 · Package 2

- [ ] Dividend taxation, realised capital gains, CGT allowance, and gain-realisation rate are
      modelled — not a flat "annual appreciation taxed" shortcut (§40 explicit "do NOT" instruction).
- [ ] Cost basis is tracked so only realised gains are taxed; unrealised gains defer tax.

**Ambiguity:** the reference-design prototype approximates GIA entirely as a fixed long-term
"drag" (~6%/yr vs ISA, stated in its own footer and in `engine.js`) instead of modelling turnover,
dividend yield, and realisation rate individually. Work-packages explicitly flags this as an
assumption that "must not become production modelling assumptions" — restating it here since it's
the most concrete instance of that warning in the whole prototype.

### 9. Cash
Spec: §78, §41 · Package 2

- [ ] Cash is a distinct asset/account type contributing to liquid wealth and liquidity coverage.

**Ambiguity:** the spec uses "cash" in two different senses — (a) an account balance under
`assets.cash` (§78) that is part of Freedom Capital/liquidity (§12, §41), and (b) a portfolio
allocation weight `portfolio.cash` (§45, §78 Simulation inputs) representing a low-return asset
class held inside a wrapper (e.g. within pension or GIA). The reference design's Overview tab
exposes both as separate fields ("Cash (£)" under Assets vs. "Cash weight (%)" under Pension
contributions & portfolio) without naming the distinction. Confirm these are intentionally two
different concepts (uninvested cash account vs. in-portfolio cash allocation) so they aren't
conflated in the shared contract.

### 10. Accessible vs locked capital
Spec: §12–13, §41–42 · Package 2

- [ ] Freedom Capital (cash + ISA + GIA + realistically-releasable property equity) and Retirement
      Capital (pension/SIPP) are calculated and surfaced as separate figures, never collapsed into
      one net-worth number (§12, §75).
- [ ] A simulation can report failure (liquidity exhaustion) while total net worth, including
      pension, remains high (§13, §42 example; golden Scenario E, §87).
- [ ] Property equity is never implicitly treated as spendable; it only becomes accessible through
      an explicitly modelled action such as sale or borrowing (§42 explicit instruction).

**Ambiguity:** §12 lists "accessible property equity where realistically releasable" as part of
Freedom Capital, but §42 says equity release actions "must never happen implicitly." These are
reconcilable (equity counts once a release action is modelled, not by default) but the boundary —
does simply *holding* a paid-down mortgage ever count toward the Freedom Capital figure shown on
Overview, or only after a release/downsizing scenario is explicitly run? — should be settled
before the accessible-capital metric is implemented, since it changes what Overview and the
liquidity-coverage metric (§41) display by default.

### 11. Deterministic year-by-year projection
Spec: §6 · Package 2

- [ ] A single reference run produces opening assets, all income/contribution/return/tax/cost
      line items listed in §6, and closing assets for every simulated year.
- [ ] The projection is explicitly documented as not the primary FIRE-safety measure (§6 final
      instruction) — i.e. it must not be the number surfaced as "success probability."

### 12. Monte Carlo investment returns
Spec: §7–10, §44–46 · Package 3

- [ ] Returns are sampled from a pluggable, documented distribution per path/year, not a fixed
      annual return (§7, §44).
- [ ] Default simulation count is 10,000 and is configurable (§7).
- [ ] Portfolio composition (equities/bonds/cash) affects simulated returns, and different
      wrappers (ISA/GIA/pension) may hold different allocations (§45).
- [ ] Zero-volatility Monte Carlo output converges to the deterministic ledger (§86 "Zero-Volatility
      Test" — critical cross-engine check).

### 13. FIRE success probability
Spec: §14–15, §76 · Package 3

- [ ] Success is defined per §14: required accessible assets are never exhausted pre-pension-access,
      required annual spending is met, the plan doesn't become insolvent, and assets remain
      sufficient to the configured terminal age.
- [ ] The headline metric is `Successful Simulations / Total Simulations` (§76, "primary FIRE
      metric") — not the deterministic reference FIRE ratio.
- [ ] Golden Scenario C (very high starting wealth → ~100% success) and Scenario D (zero assets,
      zero income, positive spending → 0% success) pass (§87).

**Ambiguity:** §14's "simple V0.3 success definition" is `Portfolio Balance > 0` in every required
year AND essential spending is funded. But §25 defines three spending levels (floor/target/
comfort), and §26 separates current vs. FIRE spending. Which spending level does "success" test
against by default — floor (minimum acceptable) or target (expected FIRE lifestyle)? The dashboard
mock (§80) references "Target success probability" against "Target spending," suggesting target,
not floor — but §14's literal wording says "essential spending," which maps more naturally to
floor. This should be pinned down explicitly, since it changes every headline probability shown
across the FIRE & Monte Carlo, FIRE Age Curve, Reverse Solver, and Scenario Comparison tabs.

### 14. Sequence-of-returns risk
Spec: §8, §70 · Package 3

- [ ] Two paths with similar long-run average return but different early-year sign can produce
      materially different retirement outcomes in the model (§8 illustrative example).
- [ ] Explicit sequence-risk metrics are reported: probability portfolio falls >20% in the first 5
      FIRE years, probability accessible portfolio falls below 2 years' expenses, and median
      recovery time (§70).

### 15. Pre-pension bridge
Spec: §13, §42 · Package 2–3

- [ ] Bridge length (pension access age − FIRE age) is calculated and simulated as its own
      constraint, distinguishable from post-pension sustainability.
- [ ] A simulation can fail specifically through bridge/liquidity exhaustion even while the
      pension balance is large (golden Scenario E, §87).

### 16. FIRE-age probability curve
Spec: §17 · Package 6

- [ ] Success probability is computed across a range of candidate FIRE ages, not just one.
- [ ] The earliest age reaching the user's target success probability is identified and surfaced
      (§17 example: target 90% → earliest age 47).

### 17. Reverse annual-savings solver
Spec: §31–32, §60 · Package 6

- [ ] Given target FIRE age, target success probability, target spending, existing assets, and
      current salary/spending, the solver returns the required annual investable surplus (§32,
      first solve step).
- [ ] The solver accounts for marginal taxation when translating between surplus and income
      (§32 final instruction).

**Ambiguity:** the reference design's Reverse Solver tab exposes exactly two modes — "Required
salary" and "Required FIRE spending" — with no third mode that solves for required annual savings
directly (as an accessible-surplus figure, before grossing up to a salary). Per §32 the salary
solve is explicitly a two-step process (surplus first, then gross salary), so it's possible the
required-savings figure is meant to be an intermediate value shown alongside the salary result
rather than its own selectable mode. Confirm whether item 17 needs a standalone UI entry point or
is satisfied as a labelled intermediate output of item 18's solve.

### 18. Reverse gross-salary solver
Spec: §32–33, §60 · Package 6

- [ ] Given the same targets as item 17, the solver returns the required gross active income,
      accounting for marginal tax (§32–33 worked example).
- [ ] Already-achieved targets, unreachable targets (bounds exceeded), and numerical tolerance are
      handled and labelled explicitly, not silently approximated (work-packages §6).
- [ ] Returned solutions satisfy the target probability when the solution is re-run through the
      full model (work-packages §6 "Done when").

**Ambiguity:** §60 lists six possible solver unknowns (salary, annual savings, FIRE age, starting
capital, spending reduction, pension contribution), but the reference design only builds UI for
two of them (salary, spending). Work-packages package 6 explicitly requires starting-capital and
pension-contribution searches "through the same bounded solver framework" even though "shown by
the reference UI" only covers age and spending-reduction modes beyond salary. This leaves at least
two required solver modes (starting capital, pension contribution) with no corresponding element
anywhere in the reference design — their UI treatment needs to be designed, not just engineered.

### 19. Marginal Pension/ISA/GIA comparison
Spec: §57–59, §82 · Package 7

- [ ] For a given increment of capital, the model reruns the full lifetime simulation once per
      candidate destination and compares FIRE probability, median wealth, and accessible wealth
      (§57–58).
- [ ] Each candidate is classified as Dominant / Near Equivalent / Assumption Sensitive / Inferior,
      and tiny numerical differences are not presented as strong recommendations (§58 explicit
      instruction).
- [ ] Tax-band boundaries are detected from tax configuration, not hard-coded to £55k (§59
      explicit instruction).

**Ambiguity — scope of "destinations":** §88 item 19 names only Pension/ISA/GIA, but §57 lists six
candidates (adds Cash, Mortgage Overpayment, Property Deposit), and work-packages package 7's
"Done when" requires "all six destinations are computed or explicitly ineligible." The reference
design's Marginal Allocation tab matches the narrower §88 wording: only Pension/ISA/GIA are run
through Monte Carlo, while Cash and Mortgage Overpayment are shown as static "reference, not
simulated" cards, and Property Deposit isn't represented at all. Confirm whether the true v0.3
MUST is the 3-way simulated comparison (§88's literal list, matching the reference design) with
cash/mortgage/property as informational extras, or the full 6-way simulated comparison (§57 +
package 7) — this materially changes engine scope and the tab's layout.

### 20. Basic single-property model
Spec: §47–50 · Package 5

- [ ] Property equity return is decomposed into appreciation, net rental yield, interest,
      maintenance, insurance, taxes, and transaction costs (§47) — not treated as a single ETF-like
      return.
- [ ] Mortgage balance, annual interest, principal repayment, and property value/equity are
      calculated year by year (§48).
- [ ] Scope is exactly one property (work-packages "Explicit scope boundaries": "do not add...
      multiple properties").

### 21. Property leverage
Spec: §48–49, §51 · Package 5

- [ ] Leverage effect on equity is shown for both a gain and a loss scenario, computed relative to
      deposit (starting equity), not relative to full property value (§49 worked example, both
      directions).
- [ ] LTV, debt-service coverage, and interest sensitivity are tracked (§49).
- [ ] Mortgage-rate scenario analysis covers at minimum 3%, 5%, 7%, 9% (§51 explicit minimum;
      work-packages package 5 "required 3/5/7/9% mortgage scenarios").

**Ambiguity:** the reference design's leverage table only computes three rows — the user's
configured appreciation rate, a fixed +5%, and a fixed −10% — with no 3/5/7/9% mortgage-rate
scenario table anywhere on the Property & Leverage tab. That table is a named MUST deliverable
(work-packages package 5) with no counterpart in the visual reference; its layout needs to be
designed, not inferred from the prototype.

### 22. Rent-vs-buy comparison
Spec: §52–53, §56 · Package 5

- [ ] Buy is compared against rent-and-invest using matching Monte Carlo market paths where
      practical, including the deposit's opportunity cost (§52, §56).
- [ ] The comparison reports expected/median net worth, P10/P90 outcomes, FIRE success
      probability, liquidity, maximum drawdown, and debt exposure — a full-plan comparison, not a
      single-year snapshot (§56 explicit output list).
- [ ] Housing cash outflow and housing economic cost are kept separate, and rent is correctly
      replaced (not double-counted) once a property is bought (§53).

**Ambiguity — design vs. spec depth:** the reference design's "Buy vs. rent — year 1 economics"
card computes only a single year's cash comparison (rent avoided vs. housing economic cost) and
explicitly notes deposit opportunity cost "is not yet netted in here." §56 and work-packages
package 5 both require a full lifetime, multi-percentile, Monte-Carlo-based comparison. The
reference design has no UI for that fuller comparison at all — this is the same kind of
design/spec gap as items 18, 19, and 23, and needs a UI decision (new section within Property &
Leverage, or a distinct view) before implementation, not just a bigger engine.

### 23. Named scenarios
Spec: §63–66 · Package 8

- [ ] Named scenario presets exist per §64: Baseline, ISA Heavy, Pension Heavy, Income Growth,
      Property Heavy, No Property, Aggressive FIRE, Conservative FIRE.
- [ ] Scenarios can be created, edited, duplicated, and saved/loaded locally with versioned inputs
      (work-packages package 8).
- [ ] All scenarios in a comparison share identical simulated market paths (common random numbers,
      §65), so displayed differences reflect strategy, not simulation noise.
- [ ] Changing one saved scenario does not mutate another (work-packages package 8 "Done when").

**Ambiguity — matrix vs. named list:** §63 additionally requires a "Required Scenario Matrix" of
5 salaries × 3 spending levels × 4 capital strategies (60 combinations, including property),
which work-packages package 8 states explicitly ("Done when: all 60 combinations are available and
reproducible"). The reference design's Scenario Comparison tab shows a flat 5-row named-strategy
table (Baseline, Pension Heavy, ISA Heavy, Salary £75k, FIRE +3 years) with no matrix UI at all.
Confirm whether the 60-combination matrix is a distinct feature living on the same tab (e.g. an
expandable/filterable table) or a separate view, since it is materially larger than anything the
reference design depicts, and batch/caching behaviour (work-packages: "batch expensive comparisons
with progress/cancellation... label any reduced-path preview") has no corresponding UI affordance
in the prototype either.

### 24. Deterministic stress scenarios
Spec: §72 · Package 9

- [ ] At minimum, deterministic stress paths exist for: 2000-style crash, 2008-style crash, high
      inflation decade, lost decade, mortgage-rate shock, property crash, and job loss (§72).
- [ ] Stress paths run through the same ledger as the rest of the model (work-packages package 9
      "Done when").
- [ ] Historical-style scenario names carry documented assumptions and do not imply an actual
      historical backtest (work-packages package 9 explicit instruction; spec §73 confirms real
      historical backtesting is a future extension, out of v0.3 scope).

**Ambiguity — no UI at all:** the reference design has no stress-testing surface anywhere across
its eight tabs. Work-packages package 9 assigns stress-scenario output to the "Where It Comes
From" tab ("reference UI tab 8 plus FIRE analysis"), but the reference design's "Where It Comes
From" (Attribution) tab only contains the five-lever income/spending bar chart — no crash/
inflation/job-loss table or chart exists to extend. This is the largest visual-design gap in the
document and should be resolved with a concrete mockup addition before engineering begins on this
item, not left to be improvised alongside the engine work.

### 25. Percentile outputs
Spec: §67–68 · Package 3

- [ ] Success probability, median/mean terminal wealth, P10/P25/P75/P90 terminal wealth, worst
      observed outcome, median FIRE capital, bridge-failure probability, and depletion probability
      are all produced (§67 minimum list).
- [ ] Wealth distribution (P10/P25/median/P75/P90) is reported at ages 40, 45, 50, 57, 65, 75, 85,
      95, separately for liquid wealth, pension, property equity, and total net worth (§68).

**Ambiguity:** the reference design's FIRE & Monte Carlo tab shows P10/median/P90/mean terminal
wealth but not P25/P75, worst-observed outcome, or the §68 age-banded distribution table/chart at
all. No tab in the reference design contains an age-by-percentile breakdown for any of the four
asset categories §68 requires. Placement (Overview? FIRE & Monte Carlo? a new element?) needs a
decision.

### 26. Seeded reproducibility
Spec: §65–66, §84 · Package 3

- [ ] Identical inputs and seed reproduce identical output exactly (§66, §86 "Monte Carlo
      Determinism").
- [ ] Every simulation result stores `random_seed`, `simulation_count`, `assumption_version`,
      `tax_config_version`, portfolio assumptions, and property assumptions (§66 explicit list).

**Ambiguity:** the spec requires this metadata to be *stored with every result* (§66) but never
states it must be shown in the UI — the reference design has no visible seed/version indicator
anywhere. Decide whether reproducibility metadata is developer/debug-only (e.g. exportable/
inspectable but not part of the normal dashboard) or a user-facing element (e.g. footer text or an
info affordance), since package 10's acceptance check ("verify... reproducibility metadata")
doesn't specify visibility either.

### 27. Sensitivity analysis
Spec: §71 · Package 9

- [ ] Sensitivity is tested for, at minimum: expected equity return, equity volatility, inflation,
      spending, salary growth, FIRE age, mortgage rate, property growth, and pension withdrawal
      tax (§71 explicit list of nine variables).
- [ ] Sensitivity output is understood as answering "which assumptions matter most," distinct in
      purpose from Monte Carlo's "what is the distribution of outcomes" (§71 explicit framing).

**Ambiguity — distinct from item 28:** the reference design's only "sensitivity"-flavoured tab
(Where It Comes From / Attribution) computes exactly five structural-lever deltas (pension
contribution +10pp, remove GIA drag, salary +£10k, retire 2 years later, reduce spending £3k/yr) —
this is item 28's income-vs-allocation attribution, not item 27's nine-variable assumption
sensitivity (equity return, volatility, inflation, mortgage rate, property growth, pension
withdrawal tax are all absent from the prototype's lever list). These read as two genuinely
different analyses that both need a place in the product; confirm they are both required as
separate outputs (e.g. a tornado-style assumption-sensitivity chart alongside the existing
lever-attribution bar chart) rather than assuming one satisfies the other.

### 28. Income-vs-allocation attribution
Spec: §34 · Package 9

- [ ] The model quantifies FIRE-probability improvement attributable to: more income, lower
      spending, better tax allocation, later FIRE, more investment risk, and property leverage
      (§34 category list).
- [ ] Output distinguishes structural levers (income/spending/timing) from wrapper-optimisation
      levers (pension/ISA), explicitly preventing over-optimising small tax differences while
      ignoring larger structural gaps (§34 final instruction; Hypothesis 3, §152–176).
- [ ] This matches the reference design's Attribution tab bar-chart pattern (five ranked levers
      with a dominant-lever insight sentence) reasonably closely — this is the one item where the
      reference design's depth already looks sufficient, modulo extending its lever list to match
      §34's full category set (e.g. it currently has no "more investment risk" or "property
      leverage" lever).

### 29. Spending sensitivity
Spec: §61 · Packages 2, 6

- [ ] FIRE age @ target success probability and required salary are computed for each of the three
      monthly-spending levels (§61 table structure: monthly spending → FIRE age → required salary
      → reference FIRE number).
- [ ] Both effects of spending changes are shown together: increased investable surplus and
      reduced FIRE capital requirement (Hypothesis 4, §178–211; golden Scenario F, §87).

**Ambiguity — no dedicated UI element:** no tab in the reference design contains a three-row
spending-sensitivity table matching §61's structure. It's plausible this belongs on the Reverse
Solver tab (its sensitivity table already has a similar shape, currently populated with different
rows) or the Scenario Comparison tab, but the reference design doesn't show it anywhere; needs a
placement decision.

## Part B — The eight reference UI tabs

Tab set and order per work-packages.md: *Overview; FIRE & Monte Carlo; FIRE Age Curve; Marginal
Allocation; Reverse Solver; Scenario Comparison; Property & Leverage; Where It Comes From.* These
eight destinations must be preserved as-is — additional required analysis goes inside them, not
into a new/different navigation structure (work-packages, "Authority and baseline").

### 1. Overview
Package 4 · MUST items surfaced: 1, 2, 3, 4, 6, 7, 8, 9, 10, 11

- [ ] Personal/target, income, spending, assets, and pension/portfolio inputs are all editable
      here, matching the reference design's five input cards.
- [ ] Whole-balance-sheet output shows liquid wealth, locked pension, and net worth as distinct
      figures (never collapsed — item 10).
- [ ] Annual cash-flow card shows gross income → pension contributions → tax/NI → take-home →
      living costs → investable surplus → savings rate → current marginal rate, all from the real
      tax engine (item 1/2), not the prototype's single-band synchronous approximation
      (`scottishTaxSync` in the design file — explicitly a placeholder for pre-engine render only).
- [ ] Values are presented in today's money (real terms) consistently, per spec §27.
- [ ] Invalid input (e.g. portfolio weights not summing to 100%, negative ages) is caught and
      cannot silently reach the engine (work-packages package 4 "Done when").

**Acceptance case:** loading the §79 example profile into these inputs and reading off Overview's
cash-flow card should reconcile against a hand-computed reference calculation for that profile
(gross £55,000, 5%/5% pension, Scottish tax) — a natural first golden test for this screen.

**Gap vs. reference design:** the reference design's asset inputs cover cash/ISA/GIA/pension only;
property (value, mortgage balance) is listed under spec §78 "Assets" but has no field on Overview
in the design — it only appears later on the Property & Leverage tab. Confirm property fields are
intentionally scoped to their own tab rather than duplicated/summarised on Overview.

### 2. FIRE & Monte Carlo
Package 4 · MUST items surfaced: 12, 13, 14, 15, 25 (partial)

- [ ] Reference FIRE number card (target spend ÷ SWR) is shown alongside — not instead of — the
      Monte Carlo success probability (spec §18: label it "Reference FIRE Number," Monte Carlo is
      authoritative).
- [ ] Headline success probability uses the real engine's simulation count (configurable,
      10,000 default per item 12) — not the reference design's fixed 700-path prototype run.
- [ ] Failure decomposition bar splits into success / pre-pension liquidity failure / portfolio
      depletion at minimum, matching §69's classification requirement (the reference design's
      three-category bar is a reasonable minimum, but §69's example additionally breaks out
      inflation and market-crash-driven failure — confirm whether those extra categories are
      needed here or satisfied by item 24's stress analysis instead).
- [ ] P10/median/P90/mean terminal wealth and accessible-wealth-at-FIRE are shown; per item 25,
      P25/P75 and worst-observed outcome are also required somewhere on this tab if this is where
      §67's full output list lives.
- [ ] Execution runs in a worker with progress/cancellation and stale-result invalidation when
      inputs change (work-packages package 4).

**Acceptance case:** golden Scenario C (very high starting wealth) should render ~100% here;
Scenario D (zero assets/income, positive spending) should render 0% with depletion as the failure
cause; Scenario E (large locked pension, zero liquid wealth) should render a bridge/liquidity
failure specifically, not a generic depletion failure (§87).

### 3. FIRE Age Curve
Package 6 · MUST items surfaced: 16

- [ ] Curve is computed across a candidate age range and plotted, with the earliest
      target-clearing age called out distinctly (matches reference design's chart + highlighted
      point + "earliest age" callout).
- [ ] Handles progress/cancellation/stale-result states like the other compute-heavy tabs
      (work-packages package 6 "Done when").

**Ambiguity:** the reference design derives the candidate age range as `[age+1, min(endAge-5,
age+21)]` — an arbitrary prototype heuristic, not a spec requirement. The real range (e.g. should
it always reach up to pension-access age at minimum, or be user-adjustable?) is undefined in the
spec and needs a product decision, not just an engineering default.

### 4. Marginal Allocation
Package 7 · MUST items surfaced: 19

- [ ] User enters an incremental amount; the engine reruns the full model per candidate
      destination and reports Δ FIRE probability, Δ accessible wealth at FIRE, and a
      Dominant/Near-Equivalent/Inferior classification per candidate (§58).
- [ ] Tax-band boundary effects are detected from configuration and reflected in the comparison,
      not hard-coded (§59).
- [ ] See item 19's ambiguity above: confirm whether Cash and Mortgage Overpayment (shown as

## Part C — Cross-cutting ambiguities (not owned by one item)

These recur across several MUST items and are worth resolving once, centrally, rather than
per-item:

1. **Spending figures: per-person or household?** (affects items 3, 5, 21–26 family of
   requirements). §21 labels the baseline range `monthly_per_person`; §79's example profile and
   the reference design apply it directly at household level for a single adult. §22's household
   model (shared vs. per-person costs) is otherwise unused anywhere else in the spec or design.
2. **"Cash" the account vs. "cash" the portfolio weight** (item 9) — same word, two different
   roles (§78 `assets.cash` vs. §45/§78 `portfolio.cash`); reference design exposes both without
   naming the distinction.
3. **What spending level defines "FIRE success"?** (item 13) — floor, target, or comfort (§25);
   §14's literal wording ("essential spending") and §80's dashboard wording ("target spending")
   point in different directions.
4. **Candidate count for marginal allocation** (item 19) — 3 (§88's literal list, matches
   reference design) vs. 6 (§57 body text and work-packages package 7).
5. **Depth of rent-vs-buy** (item 22) — year-1 snapshot (reference design) vs. full lifetime
   Monte Carlo comparison (§56, work-packages package 5).
6. **Scope of "named scenarios"** (item 23) — a short named-preset list (§64, matches reference
   design) vs. the full 60-combination salary×spending×strategy matrix (§63, work-packages
   package 8).
7. **Reverse solver mode coverage** (items 17–18) — reference design shows 2 of the 6 unknowns
   listed in §60; work-packages requires at least 4 of the 6, with no UI reference for the extra
   two.
8. **Items 27 vs. 28 are two different analyses**, not one — the reference design currently only
   builds something resembling item 28.
9. **No UI exists at all for:** the §68 age-banded wealth-distribution table (item 25), stress
   testing (item 24), assumption sensitivity (item 27), or the §61 spending-sensitivity table
   (item 29). These four are the clearest "needs a mockup before engineering" gaps between the
   reference design and the §88 MUST list.
10. **Reproducibility metadata visibility** (item 26) — required to exist (§66) but not specified
    as user-visible anywhere; reference design shows none.
11. **GIA modelling fidelity** (item 8) — the reference design's fixed ~6%/yr drag factor is
    explicitly a prototype shortcut per work-packages and must not be read as the intended
    production model.

## Part D — Non-goals of this document

Per the task this checklist was produced for:

- No engine (tax, deterministic ledger, Monte Carlo, property, solver, marginal-allocation,
  scenario, or attribution/stress) is implemented or designed here.
- No shared input/result schema, ledger interface, or market-path interface is defined or amended
  here — those remain package 1's authority per `implementation-work-packages.md` §83.
- Where this document flags a design/spec gap (e.g. missing stress-testing UI), it identifies that
  a decision and/or mockup is needed — it does not propose the mockup or the data shape itself.
