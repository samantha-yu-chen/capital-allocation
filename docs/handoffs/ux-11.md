# Handoff — UX-11: the way out of a starting situation, and the flat spending column

Baseline: `c0dbef2` (the UX-10 merge). Ticket: `docs/ux-improvement-plan.md` § UX-11 — added by this
package, after UX-1..UX-10 were all delivered, from three things the reader reported while using the
app. Presentation package: `git diff --stat` over the branch touches nothing under `src/engine/`,
`src/domain/` or `src/config/`, and `profileSchema` is unchanged. No figure on any screen moved for
the profile the app opens with — the 10,000-path FIRE run still measures **68.98%** and the property
comparison **35.18%**.

## What was reported, and what turned out to be true

| Reported | Verdict |
| --- | --- |
| "spending is the same across all years; shouldn't inflation compound?" | **The arithmetic is right.** `inflationIndices` accumulates a running product and `spendingForYear` returns `essentialReal × inflationIndex`; the ledger stores nominal and the view deflates. The flat line is the *correct* appearance of a constant standard of living on the money basis the ledger opens on. Nothing said so. |
| "if user select the default scenario, it's hard to track where it should navigate to change the settings like changing household from 1 to 2" | **A genuine dead end**, and worse than it looked: `household.adults` and `household.children` were registered at the `expert` tier, so a figure advertised on the entry-level card could not be reached from the entry-level form. |
| "the idea is very cool, but … it's prob not the best" | The situations are fine; the dead end after choosing one is what made them feel unfinished. Finding 2 is the package. |

Both fixes are presentation. The engine was not opened.

## Delivered — Finding 2: a figure that says where it lives

### The registry already knew; nothing could ask it

`src/presentation/view/field-navigation.ts` is the React-free half. It resolves a registry id to a
`FieldTarget` — the reader-facing name (through `fieldName`, like everything else on screen), the
group, the destination whose form renders that group, and the tier — and it answers three questions
nothing could answer before:

- **Where does this input live?** `GROUP_SCREEN` maps every field group to a `TabId`. The Overview
  form renders eleven of the twelve groups; Property & Leverage owns the twelfth. A jump that did
  not know this would land on a screen where the box is not rendered at all, silently.
- **Is it currently on screen?** `raiseModeFor(tier, current)` returns the smallest depth that shows
  the tier, or `null` when the reader's current depth already does. It only ever widens: someone
  looking at Everything is not narrowed because the field they asked for is essential.
- **Does this profile even have it?** `fieldTarget` returns `null` for an id the current profile has
  no input for. That is the honest answer, not a failure — a fact about a property is a fact about a
  profile that has one, and the caller renders plain text rather than a button that scrolls to
  nothing.

### The facts carry their ids, with honest arity

`StarterFact` gained `fieldIds`. The twelve facts map to one, two or three inputs each, and the list
says which: "Household" is `household.adults` + `household.children`, "Cash, ISA and GIA" is three
balances, "You pay in" is a rate and a method. "Property" is the one that depends on *shape* rather
than on values, and is written that way:

```ts
const propertyFieldIds = (profile: Profile): readonly string[] => {
  if (profile.property === null) return ['property'];               // the switch that adds one
  if (profile.property.purchase === null) return ['property.marketValue', 'property.mortgageBalance'];
  return ['property.purchase.price', 'property.purchase.deposit'];
};
```

**Only the card in use turns its facts into links.** This is the decision worth recording. A fact on
a card you have not chosen describes a profile you are not holding; sending the reader to a box with
a different number in it would be a lie, and one that looks like a bug. Unchosen cards render exactly
the `<dt>/<dd>` they always did. The links are also resolved against `props.profile` — the profile
the form holds — not against the card, because that is where the jump actually lands.

### "Not quite you?"

Four labelled jumps sit under the grid, authored in `view/starter-picker.ts` as data:

| Jump | Inputs it opens |
| --- | --- |
| Change your household | `household.adults`, `household.children` |
| Change your salary | `income.salaryAnnual` |
| Change your spending | the four current/retirement monthly figures |
| Change the age you want to stop | `personal.targetFireAge` |

A jump whose label covers more than one box says so to a screen reader (`jumpDescription`), and the
test refuses any jump whose targets include an `expert` input: if a common departure ever needs one,
the honest fix is to re-tier it, not to raise the filter for it every time.

### Household size is a `common` input now

`household.adults` and `household.children` moved from `expert` to `common`. UX-1's definition of
`common` is "what a reasonably engaged person knows about their own situation", and "two adults and
two children" is exactly that. The tier is presentation only — the values, the defaults, the
validation and the run key are all untouched, and the default form goes from 30 rendered inputs to
32, still inside UX-1's ≤ 40.

**One audit pinned the old tier, and it was updated deliberately.** No unit test did;
`tests/browser-tier-filter-ui.mjs` listed `Household` among the groups that must be hidden at the
default depth. The assertion was **inverted, not deleted**: the group must now be present at the
default depth, must still be absent from `Essential only`, and both inputs are named.

### The form serves the request, and says what it did

`ProfileForm` takes a `FieldFocusRequest` (a field id plus a strictly increasing sequence, so asking
twice is two requests and a second click still works). It widens its own filter if it must, opens
the group, scrolls the box into view and focuses it — in two effects, because the widened filter has
to render before the box exists to be focused. Above the form, `ArrivalNote` says where the reader
landed and, when the filter moved, what moved and why:

> Detail raised to "Essential + common" so that "Adults" is on screen. Nothing about your plan
> changed: which inputs are shown is a display setting, and you can set it back above.

An audit derived from the sources fails any second surface that calls `raiseModeFor`, and any surface
that calls it without rendering `tierRaiseNote`.

### The depth moved to the shell, and that is what made the raise real

The tier filter lived in `ProfileForm`'s own state. Leaving Overview unmounted the form, so
"Essential only" silently became "Essential + common" on every return — and the filter raise was
therefore **unreachable in practice**, because every jump comes from a surface (the wizard, the
Scenario screen) that unmounts the form first. This was found by the browser harness failing, not by
reading the code. The mode now lives in `App` beside the solver question. It is still display-only:
it reaches no profile, no draft, no validation and no run key.

### A select had no id to jump to

`SelectField` and `CheckboxField` generated their ids with `useId()`, so `personal.taxRegion` — a
fact on every card — was unaddressable. Both now accept an optional `controlId`, and
`profile-form.tsx` passes the registry id through `textOf(def)`, once, for every registry-described
control. Chrome confirms the Tax region fact lands on a focused `<select id="personal.taxRegion">`.

## Delivered — Finding 1: the flat column, explained where it is read

The default money basis is **not** changed, and nor is the engine. "Every result is in today's money"
is the app's contract — the `todays-money` glossary entry, `learn.ts`'s shared claim 3 and every
other screen state it — and flipping this one table to cash terms to make inflation visible would
contradict all of them.

What was missing was the sentence. In `overview-model.ts`, beside the basis it describes:

- `moneyBasisExplanation(basis)` — why the column behaves as it does on this basis, and where the
  other figure is. The real-terms wording refuses the wrong conclusion explicitly ("That is not
  inflation missing from the model: prices do rise here, every year") rather than by implication,
  and names the glossary terms that already exist instead of restating them.
- `inflationComparison(row)` — one chosen year said both ways, read off the row the ledger produced:
  *"At age 45, the £19,800 of spending shown in today's money is £27,977 in the cash of that year,
  because prices are 41.3% higher by then (inflation index 1.41)."* The current year gets its own
  sentence, because "prices are 0.0% higher" is true and useless.
- `defaultComparisonAge(rows)` — the year the pair opens on: the first row whose phase is not
  `accumulation`, so it follows the reader's own FIRE age rather than a hard-coded one.
- `MONEY_BASIS_OPTIONS` — the two labels, in one place, so the component stops writing its own.

All of it renders immediately under the money-basis control, not three cards away: a reader who has
already concluded the model is broken does not scroll to find out otherwise.

The test that makes the explanation accountable pins what it claims: twenty years on, the inflation
index has compounded past 1.4, nominal spending has grown with it, and real spending is flat to a
rounding error. An audit fails any surface offering the basis choice without the explanation, and
fails the component if the wording is typed into the TSX instead of read from the view model.

## Audits that keep working

1. Only `profile-form.tsx` may move the tier filter, and only while rendering `tierRaiseNote`.
2. Every fact id and every jump id must resolve against **every** starter situation's own profile —
   not only the one the app opens with. A dangling id fails the suite.
3. No jump target may be an `expert` input.
4. Every field group must name a destination, and the Overview and Property group lists together
   must cover the registry — otherwise an input exists that no jump can reach.
5. Fact links are gated on the chosen card and resolved against the reader's profile (asserted on
   the source), and every screen rendering the picker must hand it both `profile` and `onOpenField`.
6. No picker surface may mention `runner.run(`, `runMonteCarlo` or `onRun` — UX-9's rule, restated
   for the thing UX-11 added.
7. The surface with a money-basis control is the surface that explains it, and the wording lives in
   the view model.
8. UX-9's existing four audits are untouched and still green.

## Limitations and decisions

1. **Only the chosen card's facts are links.** A card you are not using describes a profile the form
   does not hold. Making all six sets of facts links would be more clickable and less true; the one
   that is true is the one shipped. A reader who wants the other card's figures chooses it first.
2. **A jump leaves the wizard.** The household inputs are not wizard fields, and the wizard is an
   entry point rather than a second form, so a jump lands on the destination whose form owns the
   group. The sidebar "Start here" entry always reopens the wizard, and the arrival note names the
   group so the reader can find it again without the jump next time.
3. **The tier filter now persists for the session.** That is a behaviour change beyond the ticket's
   words, and it was forced by the ticket's substance: a filter that resets on every navigation
   cannot be raised by a jump, because it is never narrow when one arrives. It is still not stored
   anywhere — a reload returns to `Essential + common`.
4. **The arrival note is dismissible but not automatic.** It stays until dismissed or until the next
   jump replaces it. An auto-dismissing notice about a setting that is still changed would be worse
   than none.
5. **The money-basis explanation is on the Overview ledger only**, because that is the only surface
   with a money-basis control; the audit is derived from the sources, so a second one has to join it.
   The FIRE, curve and scenario screens are real-terms throughout and say so through UX-3's glossary
   and UX-10's shared claim 3.
6. **The inflation pair quotes total spending, not a per-line figure.** The expanded row detail
   already reports the opening and closing indices to four decimal places for a reader who wants to
   redo any line themselves.
7. **`property.purchase.price` / `.deposit` is the property fact's target for a planned purchase**,
   and no starter situation currently plans one, so that branch is covered by the unit test rather
   than in Chrome. The two branches that do occur — no property, and an owned one — are both
   Chrome-verified.
8. **Nothing about the reader's own figures is on the picker still.** No probability, no projected
   wealth, no ranking: UX-9's rule is unchanged, and a jump is navigation, not a result.

## What a next package inherits

- **The plan is complete again**: UX-1 through UX-11 are all delivered, and there is no paste-ready
  assignment. Part D's scope boundaries stand — no engine change, no new modelled feature, no
  recommendation language, no localisation, no auto-running of expensive simulations.
- **`field-navigation.ts` is the place to ask "where does this input live?"** Anything that wants to
  point a reader at an input — a validation message, a learn section, an attribution row naming the
  lever it moved — should resolve through `fieldTarget` and hand the id to `openField`, rather than
  inventing a second way to reach a form. The two rules it enforces are that a link which cannot
  land is not offered, and that the reader's display setting never moves silently.
- **The shared-copy pattern now has five instances** — `two-numbers.ts`, `pension-relief.ts`,
  `starter-picker.ts`, `learn.ts` and the money-basis explanation in `overview-model.ts` — each with
  view data, one rendering surface, and an audit deriving its surface list from the sources.
- **The honest gap this package did not close** is that the arrival note explains a *display*
  change. It does not explain what changing the input in front of the reader will do to their
  answer, and it should not: that would be a figure nobody ran. A package that wanted to close it
  would need the marginal machinery, not more copy.
- **Re-tiering is cheap and is audited in two places.** If a future package moves a tier, expect
  `tests/presentation-inputs.test.ts` (the essential set and the ≤ 40 input count) and
  `tests/browser-tier-filter-ui.mjs` (the group lists) to have an opinion, and update them
  deliberately.
