# Handoff — UX-10: an in-app "How this works" panel, and a written learning doc

Baseline: `59fef11` (the UX-9 merge). Ticket: `docs/ux-improvement-plan.md` § UX-10, the last one in
the plan. Presentation-and-docs package: `git diff --stat` over the branch touches nothing under
`src/engine/`, `src/domain/` or `src/config/`, and `profileSchema` is unchanged. No figure on any
screen moved — the 10,000-path FIRE run still measures **68.98%** and the property comparison
**35.18%**.

## Delivered

### Two halves of one explanation, and the thing that stops them disagreeing

- `docs/learnings/how-the-model-works.md` — **1,931 words**, under the ticket's 2,500-word cap and
  asserted by a test. Six sections: one year of the model, tax and pensions, from one projection to
  many, reading the numbers, what each screen asks, what the model refuses to do.
- `src/presentation/view/learn.ts` — the same explanation as view data. `MODEL_SECTIONS` is the
  five-section walkthrough; `TAB_SECTIONS` is one section per screen, keyed on `TabId`.
- `src/presentation/web/learn-panel.tsx` — the only component that renders a section.

The assignment named the real risk: this is the first shared-copy module with enough prose that a
*contradiction* between the app and the doc is likely. Copy divergence is allowed by the ticket;
contradiction on a convention is not. So the conventions are not written twice.
`LEARN_SHARED_CLAIMS` is eight strings, and a test requires each one verbatim in both the panel data
and the markdown file:

| # | The claim | Source |
| --- | --- | --- |
| 0 | year `t` runs from one birthday to the next | ADR 002 |
| 1 | the fixed within-year event order, in full | ADR 002 |
| 2 | a recorded failure that a later good market cannot erase | ADR 002 |
| 3 | nominal in the ledger, converted back once for the screen | ADR 002, `AGENTS.md` |
| 4 | no dynamic in-run spending cut; floor/target/comfort are separate runs | `AGENTS.md` |
| 5 | the success probability is `AUTHORITY_CLAUSE` | `two-numbers.ts` |
| 6 | a sampled probability carries a margin of error | `AGENTS.md` |
| 7 | the app explains and simulates; it does not advise or predict | plan Part D |

This was verified by breaking it: rewording claim 4 in the markdown to "adjusted automatically as
markets move" failed `every shared claim is one string, carried verbatim by both the panel and the
doc` and named the claim. The markdown is compared with whitespace normalised, because a claim wraps
across lines in a `.md` file and does not wrap in a TypeScript string.

Wording another module already owns is interpolated rather than restated: `AUTHORITY_CLAUSE`,
`STARTER_ILLUSTRATION_CAVEAT` (sentence-cased into a clause, its body unchanged), and
`TAX_RELIEF_LABEL` / `TAX_AND_NI_LABEL` / `PERSONAL_NET_COST_LABEL`. A test asserts all five reach
both surfaces. If one is reworded at its source, the explanation follows it rather than going stale.

### It explains; it never reports

The panel is the one page a reader arrives at *before* they trust a number, which makes it the worst
place in the app to put a figure nobody ran. So it holds none. The suite asserts no `£` and no
percentage appears anywhere in the learn text, and no phrase that reads as advice. The Chrome
harness re-measures that on the rendered prose.

One scoping decision there: the browser check reads `.learn-paragraph` rather than the whole panel,
because a *glossary term name* may legitimately contain a figure — `Withdrawal rate (the "4% rule")`
is one — and that is a UX-3 definition's own title, not a result. The unit test, which reads the data
rather than the DOM, has no such exception and needs none.

The panel also starts nothing. Reading is free; 10,000 paths are not. An audit derived from the
sources fails any learn surface whose source mentions `runner.run(`, `runMonteCarlo` or `onRun`.

### Where it lives, and what it does to the rest of the shell

`learnOpen` is shell state beside `wizardOpen`, and the panel occupies the main column exactly as
the wizard does — so all eight destinations stay in the sidebar beside it, and `active` keeps
pointing at the screen the reader came from. That gives two things for free: the panel opens *that
screen's* section, and the way back can name it ("Back to Property & Leverage").

| Surface | Effect |
| --- | --- |
| Sidebar entry, beneath the eight tabs | Opens the panel on the current screen's section. Quieter styling than "Start here" — it explains the destinations rather than competing with them for the first click |
| Any tab click while open | Closes the panel and goes to that screen |
| "Back to <screen>" | Closes the panel, returns to the screen the reader came from |

Opening the panel is not an edit, so a published probability survives a visit to it — measured, not
assumed.

### Every claim cites the file it comes from

Each section carries `sources`, rendered as a "Where this comes from" line, and a test asserts every
cited path exists on disk (stripping the human pointer in brackets, `docs/architecture-decisions.md
(ADR 002)`). This is what makes the doc maintainable rather than decorative: an edit to a convention
has a list of the prose it invalidates, rather than a reviewer's memory.

### Audits that keep working

1. Section coverage is derived from `TABS`, not restated — a ninth destination fails the test. A
   `Record<TabId, …>` also makes it a compile error.
2. Every file under `presentation/web` that reaches `MODEL_SECTIONS`, `TAB_SECTIONS`, `learnForTab`
   or `tabSections(` must equal `LEARN_SURFACES`. Prose in two components is prose that drifts.
3. The shell must render `<LearnPanel` and offer a way in — an unreachable explanation is no
   explanation.
4. `src/engine` and `src/domain` are walked, and neither may import the learn copy. AC 4 is absolute
   and this is the cheapest way to keep it true.

computing and will fail the harnesses after it for reasons that look like their own.

## Limitations and decisions

1. **The panel replaces the main column rather than sitting over it.** A modal or a drawer would let
   a reader keep a result in view while reading about it. That is a better product and a larger
   change to the shell than a docs-and-copy package should make; the wizard established the pattern
   this follows, and the panel gets out of the way the moment a tab is clicked.
2. **`LEARN_SHARED_CLAIMS` pins conventions, not the whole text.** Everything outside those eight
   strings can drift between the doc and the app, deliberately: the two are written for readers in
   different positions, and forcing them to match sentence for sentence would mean one of them is
   wrong for its reader. What cannot drift is any statement of a rule.
3. **The doc is 1,931 words and the panel renders 1,827.** They are close but not identical, and the
   doc carries material the panel does not — the eight-question table, and the note on what the
   product authority is. Treat the doc as the fuller version.
4. **No section links to another.** `seeAlso` exists on glossary entries and there is no equivalent
   between learn sections; the panel's order is the reading order. Adding cross-links would need a
   resolution test like the glossary's, which was not worth it for eight sections on one page.
5. **The browser no-figure check is scoped to `.learn-paragraph`.** A glossary term name may contain
   a figure (`the "4% rule"`), and it is a definition's title rather than a result. The data-level
   test has no exception.
6. **Nothing points at the markdown doc from the app as a link.** The panel names the path in code
   font. The app is served as a static bundle with no route to the repository's docs, and a link
   that 404s would be worse than a path a reader can find.
7. **AC 4 is enforced structurally, not just claimed.** A test walks `src/engine` and `src/domain`
   for an import of the learn copy. The ticket's warning — that a learn panel must not adjust a
   starter situation's figures to make an example read better — is covered by the same rule plus
   UX-9's own audit, which requires any screen naming a situation to go through `<StarterPicker>`.

## What is left after this ticket

`docs/ux-improvement-plan.md` is complete: UX-1 through UX-10 are all delivered. There is no next
ticket in it, so there is no paste-ready assignment. What a next agent would want to know:

- **The plan's Part D scope boundaries still stand** and are the reason several obvious-looking
  improvements are absent: no engine change, no new modelled feature (couples optimisation, multiple
  properties, dynamic withdrawal), no recommendation language, no localisation, no auto-running of
  expensive simulations.
- **The shared-copy pattern now has four instances** — `two-numbers.ts`, `pension-relief.ts`,
  `starter-picker.ts` and `learn.ts` — each with view data, one rendering component, and an audit
  test that derives its surface list from the sources. A fifth should follow it. `learn.ts` is the
  one to copy if the copy is prose and also exists outside the app.
- **The honest gap this package did not close** is that the explanation is static text. It says what
  a percentile band means; it does not point at the reader's own band and say what theirs means. A
  contextual version — a learn section that reads the current result — would be genuinely better and
  is a real package, not a copy edit, because it would need the no-figure audit replaced with
  something that distinguishes "a figure from the reader's own completed run" from "a figure nobody
  ran".
- **`docs/learnings/` now holds the markdown doc beside the original PDF deck.** The deck is the
  user's own earlier notes and was not edited; if the two ever disagree, the markdown is derived from
  the code and the ADRs and the deck is not.
