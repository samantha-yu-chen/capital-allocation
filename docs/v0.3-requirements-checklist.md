# V0.3 acceptance audit — §88 MUST items + eight UI tabs

Status: **completed in package 10.** This was a planning artifact through packages 1–9; it is now
the acceptance record. Every box below was re-derived from the source and from a named test, not
copied from a previous status line. Where the audit found nothing behind a claim, the gap is stated
and the fix named.

## How to read this

Sources: `docs/lifetime-capital-allocation-fire-optimisation-spec-v0.3.md` ("spec", § numbers refer
to it) and `design/Web page UI specification/Lifetime Capital Allocation & FIRE Model.dc.html`
("reference design").

A ticked box means: the behaviour exists in the engine or the view layer, and a test named here
fails if it is removed. Browser evidence is in `docs/handoffs/chunk-10.md`; each figure quoted there
came from a harness run against a freshly started isolated Chrome.

The prototype (`design/.../engine.js`, `support.js`) is **not** a source of production modelling
assumptions. Its pooled accessible assets, single-band Scottish tax, fixed ~6%/yr GIA drag, 300–700
path runs and year-1-only rent/buy snapshot were not carried forward anywhere; the audit checked
each of those five specifically and records where the real model lives instead.

### What this audit changed

Two in-scope spec details had no implementation behind them. Both are fixed in package 10:

1. **§61's required-salary column** (item 29). The spending-sensitivity table had monthly spending,
   FIRE age at the target and the reference FIRE number, but not the required salary, and nothing
   else in the product solved it per spending case — the Reverse Solver's own §33 sensitivity moves
   retirement spending by £150/month, not the three configured §21 household cases. Each case now
   re-solves its own gross salary through the same bounded solver.
2. **§16's presentation labels** (item 13's context). Fragile / Moderate / Strong / High confidence /
   Very conservative existed nowhere. `confidenceBand` now supplies them as a reading aid that never
   displaces the user's own target.

One claim was **overstated rather than wrong** and is corrected here: the ledger resolves the tax
region's versioned configuration once per run and rescales it in real terms every projected year —
it does not re-select the region annually, and nothing in the model would want it to.

## Part A — The 29 §88 MUST requirements

### 1. UK tax model
Spec: §35, §78, §86 · Packages 1–2

- [x] Income tax, NI, personal-allowance taper, dividend tax, CGT and pension relief are isolated,
      independently testable functions in `src/domain/tax/` (`income-tax.ts`,
      `national-insurance.ts`, `investments.ts`, `pension.ts`, `net-income.ts`), not inlined into
      simulation logic. `tests/tax.test.ts` covers each in isolation (27 tests).
- [x] Rules are versioned by jurisdiction and tax year in `src/config/tax/uk-2026-27.ts`, with
      sources and effective dates recorded in `docs/tax-rules-2026-27.md`.
- [x] Known-example deterministic tests pass, including HMRC's own dividend and CGT examples
      (`tests/tax.test.ts`: "HMRC dividend example: £29,570 wages, £3,000 dividends", "HMRC CGT
      examples retain UK basic-band capacity").
- [x] The ledger performs one joint annual assessment per projected year rather than re-deriving tax
      per account; `tests/ledger-reconciliation.test.ts` "opening year reproduces the chunk-1
      documented reference case exactly" pins £9,927.05 income tax and £3,055.60 NI.

**Resolved ambiguity — support boundaries.** `docs/tax-rules-2026-27.md` states them explicitly, and
`tests/tax.test.ts` "runtime validation rejects unknown tax fields and nonfinite amounts" plus
"pension earnings, age, salary-floor and annual-limit violations are explicit" prove an out-of-scope
case is reported as unsupported rather than silently approximated.

### 2. Scotland support
Spec: header, §35 · Package 1

- [x] Scottish bands are a distinct versioned configuration from rest-of-UK bands; `tests/tax.test.ts`

**Resolved ambiguity — is rest-of-UK in scope?** Yes. The document header and work-packages §1 both

### 4. Essential vs discretionary expenses
Spec: §24, §78 · Package 2

- [x] Spending is split into essential and discretionary components as separate inputs at every
      level (current, retirement, per phase).
- [x] Essential spending drives the emergency reserve, the liquidity coverage check and failure
      classification; `tests/ledger-accounts.test.ts` "surplus is retained in cash until the
      emergency reserve is covered" and `tests/property.test.ts` "property operating costs and

- [x] Floor / target / comfort are separate complete runs with **no** dynamic in-run cut;
      `tests/ledger-golden.test.ts` "floor, target and comfort retirement levels are distinct runs,

**Resolved ambiguity — what "spending flexibility" means.** Static levels only. V0.3 excludes
dynamic withdrawal strategies, so flexibility is expressed by running floor, target and comfort as
separate plans, and by the §61 spending cases — never by cutting spending inside a bad path. This is
now a convention in `AGENTS.md` that no later package may weaken.

### 9. Cash
Spec: §78, §41 · Package 2

- [x] Cash is a distinct account contributing to liquid wealth and liquidity coverage, with taxable
      interest and emergency-reserve gating (`tests/ledger-accounts.test.ts` "cash is a distinct
      account contributing to liquidity coverage").

**Resolved ambiguity — two different "cash" concepts.** They are intentionally distinct and never
conflated: `assets.cash` is an uninvested settlement account inside Freedom Capital, while
`portfolios.{isa,gia,pension}.cash` is a low-return asset weight held *inside* a wrapper. They live
in different parts of `profileSchema`, and `tests/engine-units.test.ts` "portfolio returns are the
weighted nominal means of their wrapper allocation" exercises the weight without touching the
account.

### 10. Accessible vs locked capital
Spec: §12–13, §41–42 · Packages 2–4

- [x] Freedom Capital and Retirement Capital are reported separately every year and never collapsed
      into one figure (`tests/ledger-reconciliation.test.ts` "accessible, locked and net worth stay
      separable and are never collapsed"; `tests/presentation-screens.test.ts` asserts the screens
      never combine them into one headline).
- [x] A simulation can fail through liquidity exhaustion while net worth stays high — golden

- [x] Property equity is never implicitly spendable (`tests/property.test.ts` "unpaid mortgage

**Resolved ambiguity — does held property equity count toward Freedom Capital by default?** No. It
is excluded until an explicit release action (a modelled sale) occurs, which is the reading that
satisfies §42's "never happen implicitly". Overview and the liquidity-coverage metric therefore show
property equity as its own third figure, never inside liquid capital.

## Part D — What this audit does not cover

- Performance beyond the measured benchmarks in `docs/handoffs/chunk-10.md`. Runtime scales with the
  entered path count; no latency or memory ceiling is promised for a very large configured count.
- §30's **stochastic** expense shock (`annual_probability`, `mean_cost`). The spec makes it optional
  for V0.3 ("Monte Carlo should eventually support unexpected spending... V0.3 may implement this as
  optional"), and work-packages places it after the mandatory release. The deterministic half of the
  same need *is* implemented and is not a substitute: `liquidity.capitalNeeds` schedules a known
  cost at a known age and is funded, reported and reconciled like any other outflow
  (`tests/ledger-accounts.test.ts` "known capital needs are funded in the year they fall due"), and
  §72's one-year job-loss stress covers temporary unemployment deterministically. A random shock
  process is not implemented, and nothing on screen implies one is.
- The §89 deferred list: live brokerage integrations, bank feeds, regulated advice, multiple
  investment properties, couples tax optimisation, international tax, estate planning, stochastic
  employment loss, historical bootstrap, regime-switching models, dynamic withdrawal strategies and
  AI-generated recommendations. None is implemented and none is required.
- Visual pixel-matching against the reference design. The audit checked that every required analysis
  has a real home inside the eight tabs, not that a screen reproduces the mock exactly — several
  required outputs have no counterpart in the mock at all (Part C, row 9).
